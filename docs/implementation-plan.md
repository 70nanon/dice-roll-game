# チンチロダイスゲーム 実装計画

このドキュメントは、リポジトリ `dice-roll-game` で作るチンチロベースのダイスゲームについて、**ミニマムスコープの方針・ルール仮定・技術選定・進め方・チケット分解** をまとめたものです。

最初の PR はこの計画のみを対象にします。実装は計画レビュー後に進めます。**MVP 到達までのレビュー対象 PR は、この計画 PR を含めて 3 本** に収めます（セクション 7）。

MVP に含めない追加機能は [追加機能バックログ](backlog.md) にまとめています。

---

## 1. 目的

ブラウザだけで遊べる、チンチロをベースにした簡単なダイスゲームを作る。

- Web フロントのみで完結する（API / サーバー通信なし）
- GitHub Pages にデプロイする
- まずは遊べる最小実装（MVP）を優先し、演出や拡張は後回しにする

## 2. スコープ

### 2.1 MVP でやる（必須）

| 項目 | 内容 |
| --- | --- |
| プレイ形態 | 人間 1 人 vs CPU（親） |
| ルール | 3 個ダイス、最大 3 回振り、役判定、掛け金と配当 |
| 所持金 | 仮想チップのみ。初期値 100。0 になったらゲームオーバー |
| UI | セットアップ / プレイ / 結果 の 3 画面相当を 1 ページ内で切り替える |

| 品質 | 役判定・配当はユニットテストで固定する |

- サーバー、API、ログイン、ランキング
- オンライン対戦、リアルタイム同期
- 本物の金銭・課金

- 効果音、BGM、3D ダイス
- PWA、ネイティブアプリ化
- 複雑なクライアントサイドルーティング

### 2.3 MVP 後に検討するもの

本ドキュメントでは扱わず、[追加機能バックログ](backlog.md) に前提条件付きで一覧化する。着手判断は MVP 公開後に行う。

## 3. ルール仮定（レビュー対象）

チンチロには家ごとの差があるため、**このリポジトリでは次のルールで固定する**。実装前にここを承認・修正してほしい。

### 3.1 進行

1. プレイヤーが掛け金を決める（所持金の範囲、最低 1）
2. CPU（親）が最大 3 回まで振る。役が確定したら止まる
3. プレイヤーが最大 3 回まで振る。役が確定したら止まる（途中で「この目で勝負」も可）
4. 役を比較し、配当を清算する
5. プレイヤーの所持金が 0 なら終了。それ以外は次ラウンド

親は CPU 固定とする（親交代は MVP 対象外）。

### 3.2 振り方

- サイコロは常に 3 個まとめて振る
- 個別キープ（1 個だけ振り直す）はしない
- 1 回目・2 回目で役なし（目無し）なら自動で振り直す
- 3 回目も役なしなら目無し確定
- 役が付いた場合、プレイヤーは「確定して勝負」または「残り回数があれば振り直し」を選べる
- CPU は役が付いたら必ず確定する（振り直さない）

### 3.3 役（強い順）

| 強さ | 役 | 出目 | 配当（勝者から見た倍率） |
| --- | ---: | --- | --- |
| 1 | ピンゾロ | `1-1-1` | 5 倍 |
| 2 | アラシ（ゾロ目） | `2-2-2` … `6-6-6` | 3 倍 |
| 3 | シゴロ | `4-5-6`（順不同） | 2 倍 |
| 4 | 通常の目 | ペア + 残り 1 個。残りが目（1〜6）。目が大きい方が強い | 1 倍 |
| 5 | 目無し | 役なし（3 回振り切り、または比較時に役なし） | 1 倍負け |
| 特殊 | ヒフミ | `1-2-3`（順不同） | 2 倍負け |

同じ役どうしの強さ:

- アラシは出目の値が大きい方が強い（`6-6-6` > `2-2-2`）。ピンゾロはアラシより上で単独最強
- 通常の目は目の値が大きい方が強い（6 目 > 1 目）
- 同じ役・同じ目ならあいこ（掛け金は戻る）

### 3.4 勝敗と配当

比較は「役の強さ」で行い、同じランクならタイブレーク（アラシの出目、通常の目の値）を見る。

清算:

- プレイヤー勝ち: 所持金 += 掛け金 × プレイヤー役の倍率
- プレイヤー負け: 所持金 -= 掛け金 × **相手側の負担倍率**
  - 自分がヒフミ: 2 倍払い
  - 自分が目無し: 1 倍払い
  - 相手が上の役: 相手役の倍率で払う
- あいこ: 所持金変化なし

所持金が足りない負けは、**所持金全額まで**支払ってゲームオーバーとする（借金は作らない）。

### 3.5 乱数

`Math.random()` で 1〜6 を出す。暗号学的乱数は使わない。テストでは乱数を注入できるようにする。

## 4. 技術選定

ミニマムかつ GitHub Pages 向きの構成にする。

| 層 | 選定 | 理由 |
| --- | --- | --- |
| 言語 | TypeScript | 役判定を型とテストで固定しやすい |
| バンドラ | Vite | 開発体験が良く、静的書き出しが Pages と相性が良い |
| UI | React | 画面状態（セットアップ / 振り / 結果）の切り替えが素直 |
| ルーティング | なし（画面は state で切替） | Pages のサブパスでも 404 を気にしなくてよい |
| スタイル | 素の CSS（CSS Modules 可） | ゲーム画面は独自見た目になりやすく、ユーティリティ CSS は必須ではない |
| テスト | Vitest | Vite と同じ系統。ドメインロジックの単体テストに使う |
| CI | GitHub Actions | lint / test と Pages デプロイ |
| ホスティング | GitHub Pages | 要件どおり。公開 URL は `https://70nanon.github.io/dice-roll-game/` を想定 |

採用しないもの:

- Next.js / サーバーコンポーネント（Pages の静的公開には過剰）
- バックエンド、DB、認証
- Redux 等の大型状態管理（`useReducer` で足りる）

Vite の `base` はリポジトリ名に合わせて `/dice-roll-game/` にする。これを忘れると Pages 上で JS/CSS が 404 になる。

## 6. 画面と状態

### 6.1 画面

1. **開始**: ルール一言、所持金、スタート
2. **ベット**: 掛け金入力、確定
3. **親のターン**: CPU の出目表示（自動進行でよい）
4. **子のターン**: 「振る」ボタン。役が付いたら「この目で勝負 / 振り直す」
5. **結果**: 役の比較、配当、次ラウンド or ゲームオーバー

MVP ではページ遷移せず、同じページ内で切り替える。

### 6.2 ゲーム状態の核

```ts
type GamePhase =
  | "idle"
  | "betting"
  | "dealerRoll"
  | "playerRoll"
  | "result"
  | "gameOver";

type GameState = {
  phase: GamePhase;
  chips: number;
  bet: number;
  dealer: RollState;
  player: RollState;
};
```

`RollState` は「残り振り回数」「直近の 3 出目」「確定した役」を持つ。

## 7. 進め方

### 7.1 PR の本数を優先する

MVP まではレビュー回数を減らすことを優先し、**PR は 3 本**（本計画を含む）にする。

| # | PR | 中身 | レビュー観点 |
| --- | --- | --- | --- |
| 1 | T00 | 本計画ドキュメント | 方針・ルール・チケットの合意 |
| 2 | T01 | 土台（Vite/TS/React・CI・Pages）とルール実装（役判定・配当・進行 + テスト） | ルールがコードとテストで正しく表現されているか |
| 3 | T02 | 遊べる UI 一式（画面・CPU 進行・結果・再開・見た目） | 実際に遊べるか、状態の持ち方が妥当か |

1 PR が大きくなる代わりに、レビューしやすさは PR の中で担保する。

- **コミットを論理単位で分ける**（例: `scaffold` → `役判定` → `配当` → `進行`）。コミット単位で読めば差分は小さい
- **ドメインと UI をディレクトリで分ける**ので、ファイル単位でも読む順番が決まる
- PR 本文に「どのファイルから読むか」を日本語で書く
- MVP 範囲を超える変更を混ぜない（超えるものは [バックログ](backlog.md) へ）

### 7.2 順序と依存

```text
T00 計画（本 PR）
  └─ T01 土台 + ルール実装
       └─ T02 遊べる UI 一式  ← ここで MVP 完了
            └─ 以降は backlog.md から選ぶ
```

T01 と T02 は依存するため並行しない。T01 のマージ時点で Pages にプレースホルダが公開され、T02 のマージで遊べる状態になる。

### 7.3 レビューで見てほしい点

- ルール仮定（特にヒフミ / 目無しの支払い、CPU が振り直さないこと）
- 技術選定（React でよいか）
- PR 3 本という粒度でレビューが成立するか（分けたい単位があれば指定してほしい）
- GitHub Pages を有効化するリポジトリ設定は人手作業になること

### 7.4 リポジトリ設定（人手）

コード側の workflow を入れたあと、GitHub リポジトリで次が必要になる。

1. Settings → Pages → Source を GitHub Actions にする
2. 初回デプロイ後、公開 URL を README に書く

この作業自体はチケット T01 の完了条件に含める（設定は T01 マージ後に一度だけ）。

### T01 土台とルール実装（公開経路まで通す）

| 項目 | 内容 |
| --- | --- |
| 依存 | T00 マージ |
| PR | 2 本目 |
| 主な変更 | `package.json` / `vite.config.ts` / `.github/workflows/` / `src/domain/` |

**目的**

ビルドと公開の経路を作り、同じ PR でチンチロのルールをテスト付きで確定させる。UI はまだプレースホルダのままにする。

**サブタスク（コミット単位の目安）**

1. **スキャフォールド**: Vite + TypeScript + React を初期化し、`base: "/dice-roll-game/"` を設定する。TypeScript strict と ESLint を有効にする
2. **CI / Pages**: PR で `lint` と `test` を回す workflow、`main` push で build → Pages へ deploy する workflow を追加する
3. **役判定**: 3 出目から役を返す純関数。ピンゾロ / アラシ / シゴロ / 通常の目 / ヒフミ / 目無し。出目の順番は結果に影響しない。境界（`1-1-2` は 2 目、`1-2-4` は目無し）をテストで固定する

5. **ラウンド進行**: ベット → 親が振る → 子が振る → 清算 の遷移を reducer で表す。振り回数（0〜3）、役確定、「勝負 / 振り直し」を状態に持つ。乱数は注入可能にしてテストから固定する
6. **README**: ローカル起動手順（`npm install` / `npm run dev` / `npm test`）と Pages の設定手順を書く

**レビューの読み順（PR 本文にも書く）**

`src/domain/hand.ts` → `payout.ts` → `game.ts` → 各テスト → workflow → scaffold 設定ファイル

- [ ] `npm run dev` / `npm test` / `npm run build` が通る
- [ ] 役判定・配当・進行のテストがあり、UI なしで 1 ラウンドを最後まで進められる
- [ ] ゲームオーバー条件がテストされている
