# 追加機能バックログ

MVP（[実装計画](implementation-plan.md) の T00〜T02）には含めないが、あとから足せる機能の一覧です。

このドキュメントは「やると決めたリスト」ではなく**候補リスト**です。着手するときに実装計画側へチケットを起こします。

各項目には **前提** を書いています。前提が揃っていない機能に着手すると、その機能の PR の中で基盤まで作ることになり差分が膨らむので、先に前提を済ませます。

---

## 1. 前提となる基盤（土台側）

複数の機能から必要になる共通の土台です。これ自体は単体では遊びに影響しないため、**必要になった最初の機能とセットで入れる**のが基本です。

| ID | 基盤 | 内容 | これが必要な機能 |
| --- | --- | --- | --- |
| B1 | 永続化層 | `localStorage` の読み書きを 1 箇所にまとめる。スキーマのバージョン管理、壊れた値の復旧、リセット | F11, F12, F13, F21 |
| B2 | アニメーション基盤 | ダイスの状態遷移に合わせた演出の入れ口。`prefers-reduced-motion` の尊重、演出中の入力ロック | F01, F02, F03 |
| B3 | サウンド基盤 | 音源の読み込み、ミュート設定、初回タップまで再生しないブラウザ制約への対応 | F04 |
| B4 | 設定・ルール可変化 | 倍率や初期チップ、振り回数をハードコードから設定オブジェクトへ移す。ドメイン関数が設定を受け取る形にする | F14, F15, F22 |
| B5 | 多人数ドメイン | ドメインを「親 1 + 子 1」から「親 1 + 子 N」へ一般化する。清算を全員分のループにする | F31, F32, F33 |
| B6 | プレイヤー抽象化 | 「人間 / CPU」を戦略インターフェースとして切り出す。CPU の判断ロジックを差し替え可能にする | F16, F31, F32 |
| B7 | 通信層（サーバー） | API またはリアルタイム同期の口。**MVP の「通信なし」方針を破る**ため、採用判断が必要 | F33, F34, F35 |
| B8 | E2E テスト基盤 | Playwright 等でブラウザ上の 1 ラウンドを自動で流す | F41 |
| B9 | ルーティング | 画面を URL に対応させる。Pages のサブパスと 404 の扱いを決める必要がある | F36, F42 |
| B10 | i18n 基盤 | 文言を辞書へ外出しする。現状は日本語直書き | F43 |

## 3. ゲーム性・ルール

### F11 所持チップの保存

| 項目 | 内容 |
| --- | --- |
| 前提 | MVP 完成、B1 |
| 変更範囲 | ドメイン境界 + UI |
| 規模 | 小 |

リロードしてもチップが続く。リセットボタンを必ず付ける。壊れた保存値は初期値に戻す。

### F12 戦績・履歴 ✅ 実装済み（T03）

| 項目 | 内容 |
| --- | --- |
| 前提 | MVP 完成（**セッション内に限れば B1 は不要**） |
| 変更範囲 | ドメイン + UI |
| 規模 | 中 |

勝敗数、最大チップ、役の出現回数。ラウンドごとの出目ログ表示。

当初は前提に B1（永続化）を挙げていたが、B1 が必要なのは**リロードをまたいで残す場合だけ**で、セッション内の履歴は reducer に記録を積むだけで足りる。永続化は F11 で扱う。

### F19 ラウンド数を決める（試合制） ✅ 実装済み（T03）

| 項目 | 内容 |
| --- | --- |
| 前提 | MVP 完成、F12（終了時に見せる戦績がないと締まらない） |
| 変更範囲 | ドメインの進行 + UI |
| 規模 | 中 |

無制限（破産まで）に加えて 5 / 10 ラウンドの試合制を選べるようにし、規定ラウンド終了で戦績を出す。既定は無制限のままにして、これまでの遊び方を壊さない。

### F13 実績・称号

| 項目 | 内容 |
| --- | --- |
| 前提 | F12（履歴の集計がないと判定できない） |
| 変更範囲 | ドメイン + UI |
| 規模 | 中 |

「ピンゾロ 3 回」「10 連勝」等。履歴の集計結果から導出する。

### F14 ルール設定のカスタマイズ

| 項目 | 内容 |

## 4. 対戦形態

### F31 CPU 複数人テーブル

| 項目 | 内容 |
| --- | --- |
| 前提 | MVP 完成、B5、B6 |
| 変更範囲 | ドメイン全体 + UI レイアウト |
| 規模 | 大 |

親 1 + 子 3 のような卓。清算が全員分になり、画面も席の表示が必要になる。ドメインの型が変わるため、他機能より先に入れると後続が楽になる。

### F32 ローカル 2 人対戦（端末を渡す）

| 項目 | 内容 |
| --- | --- |
| 前提 | MVP 完成、B6（+ 3 人以上にするなら B5） |
| 変更範囲 | ドメイン + UI |
| 規模 | 中 |

同じ端末で交代しながら遊ぶ。出目を隠す・見せる切り替えの扱いを決める必要がある。通信は不要。

### F33 オンライン対戦

| 項目 | 内容 |
| --- | --- |
| 前提 | B7、B5。**「通信なし」方針の変更が必要** |
| 変更範囲 | 全体 + サーバー新規 |
| 規模 | 特大 |

部屋作成、同期、切断復帰、不正対策（乱数をサーバー側に置く）。GitHub Pages だけでは完結せず、別のホスティングが必要になる。

### F34 オンラインランキング

| 項目 | 内容 |
| --- | --- |
| 前提 | B7、F12 |
| 変更範囲 | 全体 + サーバー新規 |
| 規模 | 大 |

スコア送信は容易に改ざんできるため、サーバー側の検証方針を決めないと意味のある値にならない。

### F35 リプレイ共有

| 項目 | 内容 |
| --- | --- |
| 前提 | F12（履歴）。URL 共有なら B9、サーバー保存なら B7 |
| 変更範囲 | ドメイン + UI |
| 規模 | 中 |

出目の列を共有して同じ展開を再現する。乱数注入の仕組みがそのまま使える。

### F36 画面の URL 対応

| 項目 | 内容 |
| --- | --- |
| 前提 | B9 |
| 変更範囲 | UI |
| 規模 | 小 |

ルール説明や設定に直接リンクする。Pages のサブパスで 404 にならない構成（ハッシュルーティング等）を選ぶ。

## 7. 着手するときの進め方

1. この一覧から項目を選び、前提が揃っているか確認する
2. 足りない前提（B 番号）があれば、その機能の PR に含めるか、前提だけを先に入れるか決める
3. 実装計画の「チケット」に追記してから実装する
4. ルールに関わる変更（F14, F16, F17, F18 など）は、実装計画セクション 3 のルール定義も同じ PR で更新する
